# Massive News 수집 결과 및 소스 비교 보고서

- 작성일: 2026-10-10
- 소스: Massive Stocks News API, `GET /v2/reference/news`
- 요청 범위: 2016-06-22 ~ 2026-10-09 (양 끝 날짜 포함)
- 대상: `configs/universe.yaml`의 9개 티커 (현재 `status: TBD`)
- 구현: `src/capstone/data/massive_news.py`, `scripts/fetch_massive_news.py`
- 테스트: `tests/data/test_massive_news.py` (`./.venv/bin/pytest tests/data/test_massive_news.py -q` 실행 결과 25 passed; 가짜 응답/세션을 사용하는 모의 테스트)
- 로컬 산출물: `data/raw/massive_news/` (Git ignore 대상, 커밋하지 않음)
- 공식 문서: [Massive News API](https://massive.com/docs/rest/stocks/news)

## 1. 결론

- 로컬 Massive 산출물은 **9개 티커, 총 44,192개 티커별 행**, 연도별 JSONL 57개, 약 71.3 MB다. 기사 ID를 전역 기준으로 보면 고유 ID는 35,277개이며, 같은 기사가 여러 티커에 연결되어 있다.
- 기사 발행 시각은 `published_utc` 기준 **2018-11-05 22:50:00 UTC ~ 2026-10-09 17:15:00 UTC**다. 요청은 2016-06-22부터 시작했으나, 그 이전에 해당하는 레코드는 현재 파일에서 확인되지 않았다.
- 실행 기록에는 1,125건의 요청과 1,125건의 성공이 있다. 1,125개 티커-월 구간을 완료했고 재시도, 429, 5xx, 연결 오류는 모두 0회였다. 요청 기록상 실제 API 호출 과정은 성공했지만 공급자 측 기사 완전성을 입증하지는 않는다.
- JSONL 파싱 오류, 필수 ID/발행 시각 누락, UTC 연도와 파일 파티션 불일치는 검사한 44,192행에서 발견하지 못했다.
- 기존 Alpaca/FNSPID 보고서는 각각 더 이른 기간을 포함한다고 기록한다. **현재 `data/raw/`에는 Massive 데이터만 있어** 기존 보고서의 Alpaca/FNSPID 수치는 그 보고서에 기재된 과거 결과로 비교하며, 현재 원본과 대조해 재검증한 수치가 아니다.
- 세 소스의 행 수와 텍스트 필드는 정의가 달라 직접적인 품질 우열이나 기사 전문 커버리지 순위로 해석할 수 없다.

## 4. 필드와 내용 특성

검사는 필드 존재 여부와 자료형·길이·집계값만 사용했으며 기사 제목, 설명, 본문 값은 출력하거나 보고서에 복사하지 않았다.

| 필드/검사 | 결과 |
|---|---:|
| `id`, `published_utc`, `title`, `author`, `article_url` | 각 필드 44,192행에서 비어 있지 않음 |
| `publisher` 객체 | 44,192행 |
| `description` | 43,152행 (97.6%); 문자열 길이 중앙값 192자 |
| `keywords` 비어 있지 않음 | 29,962행 (67.8%) |
| `insights` 비어 있지 않음 | 16,737행 (37.9%) |
| `image_url` 비어 있지 않음 | 44,109행 (99.8%) |
| `amp_url` 비어 있지 않음 | 19,481행 (44.1%) |
| `article_url` 프로토콜 | HTTPS 43,782행; HTTP 410행 |

`description`은 API의 설명 필드이며 원문 기사 전문과 동일하다고 확인되지 않았다. `insights`는 일부 기사에만 있는 구조화된 티커/감성 인사이트다. 빈 `insights`를 부정 감성이나 뉴스 부재로 간주해서는 안 된다.

`publisher.name` 상위 출처는 The Motley Fool 20,584행, Zacks Investment Research 9,050행, Benzinga 5,397행, MarketWatch 3,009행, Investing.com 2,871행, Seeking Alpha 1,703행, GlobeNewswire Inc. 1,493행이다. 앞의 두 출처가 행의 상당 부분을 차지하므로 공급자 구성 변화가 모델 성능에 미치는 영향도 점검 대상이다.

## 5. 중복과 티커 태그

- 동일 티커 폴더 안의 중복 ID는 0건이다.
- 전 티커를 합친 44,192행 중 전역 고유 ID는 35,277개다. 7,217개 ID가 둘 이상의 티커 폴더에 나타나며, 반복된 티커 행은 총 8,915개다. 이는 여러 티커가 연결된 같은 기사가 티커별 수집 결과에 각각 보존된 경우와 일치한다.
- `tickers` 배열이 2개 이상인 행은 37,844개(85.6%)다. 배열 크기의 중앙값은 4, 95백분위는 17, 최댓값은 340이다. 조사한 모든 행에서 조회 티커가 해당 배열에 포함돼 있었다.
- 티커별 모델 입력을 만들 때는 같은 기사를 다른 티커 맥락에서 사용할 수 있다. 반면 통합 이벤트 테이블에서는 기사 하나와 기사-티커 관계를 분리하는 구조가 적절하다.

## 6. 기존 Alpaca/FNSPID 보고서와 비교

현재 raw 폴더에는 Massive 데이터만 있다. 아래 Alpaca/FNSPID 값은 `reports/alpaca_news_report.md`와 `reports/fnspid_news_report.md`에 기재된 과거 분석 결과이며, 이번 점검에서 해당 두 raw 데이터셋을 재집계하지 않았다.

| 항목 | Massive 현재 raw 집계 | Alpaca 보고서 기재값 | FNSPID 보고서 기재값 |
|---|---|---|---|
| 행 수 | 44,192 티커별 행 | 49,163 티커별 행 | 45,853 CSV 행 |
| 보고서 기준 기간 | 실제 `published_utc`: 2018-11-05 ~ 2026-10-09 | `created_at`: 2015-01 ~ 2026-10-07 | `Date`: 2009-08-12 ~ 2024-01-09 |
| 기록/시간 필드 | `published_utc`, 모두 UTC offset 포함 | `created_at`, `updated_at`; 보고서는 API 구간 필터가 `updated_at` 기준이라고 분석 | `Date`; 보고서는 시각이 정각에 몰리는 등 정밀도 의심을 기록 |
| 텍스트 관련 필드 | `description` 97.6%; 전문 여부 미확인 | `content` 69.5%, `summary` 47.7% (고유 ID 기준) | `Article` 약 70.3% 비어 있지 않음; 본문 열 존재 |
| 다중 티커/중복 | 행의 85.6%가 다중 티커 태그; ID는 티커 간 중복 | 보고서에 다중 티커 64.9%, 중앙 태그 수 3, 최대 2,649; 49,163행/39,645 고유 ID | 행은 `Stock_symbol` 단일 열 기준; 보고서는 ID 기준 전역 중복 수 미기재 |
| 공급자별 특성 | `insights` 37.9%, publisher 객체·키워드 제공 | Benzinga 기반; `created_at`을 시점 정합에 쓰도록 권고 | 정적 데이터셋; 2024년 이후 없음, 날짜 시각 정밀도 확인 필요 |

이 수치들은 수집 기간 종료일, 공급자, 행 단위, 텍스트 필드 정의 및 중복 기준이 다르다. 따라서 행 수가 많다는 이유만으로 커버리지가 더 좋다고 결론 내리지 않는다. 특히 Massive의 `description`과 Alpaca/FNSPID의 `content`/`Article`은 의미가 같은 필드가 아니어서 포함률을 직접 비교할 수 없다.

Massive는 현재 파일에서 2018년 말부터 2026년까지 관측되며, FNSPID 보고서의 2009~2014 구간은 제공하지 않는다. 반대로 Massive는 FNSPID 보고서의 종료 시점 이후인 2024~2026년을 포함한다. Alpaca 보고서는 Massive보다 2015~2017년의 앞선 관측을 기록한다. 세 소스를 결합하면 기간 연장에 도움이 될 수 있지만, 실제 동일 기사 중복은 URL/정규화 제목/발행 시각으로 별도 확인해야 한다. 소스 ID를 서로 같은 식별 체계라고 가정하지 않는다.

## 7. 시점 정합과 모델 입력 시 주의

- Massive `published_utc` 44,192개 모두 날짜 파싱 및 시간대 검사가 통과했고 UTC 기준 파일 연도와 일치했다. 이것은 필드 형식 검사이지, 공급자가 정의한 최초 공개 시각이 거래 시스템에서 실제 관측 가능했던 시각인지 검증한 것은 아니다.
- Alpaca 보고서는 API 필터가 `updated_at`을 기준으로 동작하는 것으로 분석하고 피처의 시점에는 `created_at`을 권고한다. FNSPID 보고서는 `Date`의 일부 정각 시각이 실제 발행 시각을 반영하는지 미확인이라고 명시한다. 이 출처별 차이를 통합 과정에서 보존해야 한다.
- Massive에는 미국 장 마감 후·휴장일 기사도 있을 수 있다. 거래 캘린더에 맞춰 해당 시각에 사용할 수 있었던 기사만 반영하고, 장 마감 이후 기사는 다음 거래일로 넘기는 규칙을 정해야 한다.
- 기사 없는 날과 감성 인사이트가 없는 기사는 서로 다른 상태다. 일별 집계에서 각각 구분할 결측/0 처리 기준이 필요하다.

## 8. 레포 규칙과 구현 현황

- `AGENTS.md`는 원본 데이터를 `data/raw/`에 보관하고 Git에 커밋하지 않도록 한다. `.gitignore`도 `data/raw/*`를 제외하고 있어 현재 raw 데이터는 코드 리뷰용 저장소 산출물과 분리되어야 한다.
- 프로젝트 목적은 SOXX 상위 10개 종목이지만 실제 `configs/universe.yaml`은 9개 티커이며 `status: TBD`다. Alpaca 보고서도 임시 목록이 SOXX 상위 구성과 다르다고 지적한다. 모델 비교 전에 유니버스를 확정해야 한다.
- `AGENTS.md`/`HARNESS.md`는 `verify.yml`이 checkout만 하는 빈 스텁이라고 설명하지만, 현재 `.github/workflows/verify.yml`은 의존성을 설치하고 `python -m pytest`를 실행한다(린트는 placeholder). 이 부분은 레포 문서와 실제 CI 사이의 차이다.
- Massive 테스트는 가짜 응답/세션을 사용하며, `./.venv/bin/pytest tests/data/test_massive_news.py -q` 실행 결과 25 passed였다. 이번 보고서의 데이터 통계는 저장된 수집 로그에서 확인했다.

## 9. 한계와 미확인 사항

1. Massive News API에서 전체 기간 데이터에 접근 가능하다고 확인했지만, 이번 수집은 2016-06-22부터 요청했음에도 실제 로컬 레코드가 2018-11-05보다 이르지 않다. 이 공백이 공급자 커버리지, 해당 티커의 실제 기사 부재, 요청·수집 과정 중 무엇 때문인지는 현재 자료만으로 판단할 수 없다.
2. 체크포인트 완료는 해당 월 페이지 순회가 코드상 끝났다는 뜻이다. 모든 공급자 뉴스가 응답에 포함됐다는 뜻은 아니다. run log에도 수집한 계획/응답의 완전성을 독립 검증한 정보는 없다.
3. 현재 `collect_symbol()`은 시작일/종료일이 동일한 완료 월을 재실행 시 건너뛴다. 실행 도중 새로 추가된 같은 달 기사를 당일 재실행으로 가져오지는 않는다. 종료 범위가 바뀌면 해당 월은 다시 조회되지만, 지속 갱신 정책은 별도 확인이 필요하다.
4. 조회당 1,000개 제한과 `next_url` 페이지네이션은 구현되어 있다. 이 실제 실행은 요청 수와 월 구간 수가 같고 페이지 추가 요청 기록이 없어 실제 다중 페이지 경로는 수집 결과로 검증되지 않았다. 모의 테스트에서는 페이지네이션 로직을 포함해 검증했으며, 전체 25개 테스트가 통과했다.
5. 외부 출처 원문 전문 제공 여부, 소스 간 기사 중복, 2016~2018년의 실제 공급자 측 커버리지는 미확인이다.

## 10. 권장 후속 작업

1. 팀에서 9개 임시 티커와 분석 기간을 확인하고 유니버스를 확정한다.
2. Alpaca/FNSPID 원본을 확보해 보고서의 과거 집계를 재확인한 뒤, 세 소스의 원본을 출처별로 보존하면서 공통 기사 테이블과 기사-티커 연결 테이블을 설계한다.
3. URL·제목·발행 시각을 이용해 소스 간 중복 후보를 표시하고, 자동 삭제 전에 샘플을 검토한다.
4. `published_utc`, `created_at`, FNSPID `Date`를 원본 필드와 출처 메타데이터를 유지한 채 공통 UTC 컬럼으로 정규화한다.
5. 거래 캘린더 기반으로 장중/장후/휴장일 적용 규칙을 구현하고 일별 티커 기사 수·결측 커버리지를 점검한다.
6. 전처리·품질 검사 결과를 `data/interim/` 및 별도 보고서에 기록한 뒤, 시간순 walk-forward 평가에 사용할 피처를 만든다.
